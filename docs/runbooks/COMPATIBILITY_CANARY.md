# Compatibility Shield maintainer Canary

This is a local observation harness, not a scheduled service or a live PASS claim.
Use alongside [real-device acceptance](REAL_DEVICE_ACCEPTANCE.md). The deterministic
Canary model tests do not establish real Chrome scheduling, UI, or physical audio.

## Preconditions

1. Create a **dedicated Chrome 120+ profile outside this repository**, with sync off.
   Do not point automation at the owner's everyday profile or export its cookies.
2. The owner must manually sign in to ChatGPT in that profile. No login credentials,
   cookies, browser profiles, keys, or private conversations belong in evidence.
   Without that login, the live result remains **PENDING: OWNER_LOGIN_REQUIRED**.
3. Load this working tree's `extension/` unpacked. Close other ChatGPT tabs in this
   profile. Keep exactly one idle, unpinned, ungrouped, non-split synthetic test tab.
   After closing old test tabs, reload the extension if stale connections remain.
4. Select a non-private local WAV in options, test it **before** recording, enable
   automatic notifications and optional tab colors. Do not test audio or run other
   extension jobs during a recording; the playback counter is extension-wide.
5. Open `chrome-extension://EXTENSION_ID/canary.html` in another Chrome window.
   Obtain the extension ID from `chrome://extensions`. The page requests no new
   permissions and sends only read-only `GET_DIAGNOSTICS` messages to the test tab.

## Run

1. Start fresh observation while the test tab is idle. Wait for
   `WAITING_FOR_GENERATION`; this establishes the playback baseline.
2. In the test tab, submit only the synthetic prompt shown on the Canary page:
   “Write a numbered list of 100 imaginary planet names. Use no personal information.”
3. Observe generating/yellow, then switch away while it is still generating.
   Keep the test tab hidden and unfocused. Do not refocus it to induce completion.
4. The harness polls storage, live diagnostics, actual group color and window focus
   every 500 ms. It requires ordered waiting → generating/yellow →
   background/unfocused → complete/blue, one additional successful extension
   playback, and healthy/degraded compatibility. A transport event alone cannot
   satisfy any completion assertion.
5. Check the human confirmation only if exactly one sound was actually heard.
   PASS additionally requires at least five seconds of stable completion with no
   second playback. Monitoring continues after PASS until **Stop recording**;
   later duplicate playback or refocus changes the current result to FAIL.
6. Stop recording before refocusing the target. Copy only the JSON from the page.
   Its schema is [compatibility-canary.schema.json](../compatibility-canary.schema.json).
   The last 120 samples and four stage timestamps are bounded; no raw DOM,
   prompt/response, URL/title, tab ID, WAV/name, cookie or credential is exported.
   The harness never saves files or uploads telemetry. Add a separate, non-private
   evidence header identifying date, Chrome/OS version and working-tree revision.

A completion too fast to observe in the background cannot pass. Start another
synthetic run rather than editing the result. A run times out after ten minutes.
Observation failure, target closure, multiple connected tabs, refocus, interrupted
jobs and duplicate playback are failures or unmet preconditions, not green results.
The counter proves extension-reported successful playback; human confirmation is
still required for physical audibility. Polling can miss very brief transitions.

## Additional scenarios

For a second job, reload the test page after the first recording to establish an idle
baseline, then run again in the same synthetic conversation. Separately use real-device
scenarios D/E/F/G for uninterrupted same-tab reuse, manual stop, worker suspension,
and ownership safeguards. Record them separately; this normal-completion harness
does not claim to automate those acceptance cases. Unit/integration tests cover
those paths deterministically.

No Chrome profile has been launched and no live PASS has been generated by preparing
this harness. Owner login, an eligible test tab, configured non-private audio and
fresh human audio confirmation remain the live acceptance prerequisites.
